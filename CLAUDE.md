# Sky Team Online

Online 2-player, cooperative web version of the board game Sky Team (pilot + co-pilot land a plane by placing dice silently), the first game of a planned private multi-game platform (like Board Game Arena). Personal/learning project. Master plan: `docs/PLAN.md` (the epics and their order); work is split into **epics** (one per game, plus the shared Platform), each in `docs/epics/<epic>/` with an `EPIC.md` (goal, phase table) and one file per phase (goals, scope, tasks, checklist). Phases are numbered from 01 inside each epic and named after it ("Sky Team 12", "Platform 04"). Technical references are in `docs/reference/`. Follow the suggested order in the master plan.

## Stack (decided)

- TypeScript strict everywhere, pnpm workspaces monorepo (Platform 05 layout): `packages/engine` (`@platform/engine`, game-agnostic), `packages/protocol` (`@platform/protocol`, the wire protocol), `packages/server`, `packages/web` (`@platform/web`, the client shell: pages, router, connection), `packages/ui` (`@platform/ui`, the client kit: shadcn components, theme, i18n, the `GameClientModule` contract); each game in `games/<id>/`: Sky Team's rules `games/sky-team/rules` (`@sky/rules`) and UI `games/sky-team/client` (`@sky/client`)
- Server: Node 20+, Express, Socket.IO, Zod for every incoming payload
- Client: React + Vite, Tailwind CSS v4 (`@tailwindcss/vite`), Zustand for the latest server view
- shadcn/ui ONLY for lobby, dialogs, toasts, tooltip/popover, select/tabs. Add components one at a time with `pnpm dlx shadcn@latest add <name>` in `packages/ui` (then make its imports relative: `../utils`, `./button`). The cockpit board, dice, tracks and alarm board are custom components (Tailwind + SVG).
- Tests: Vitest (+ fast-check fuzzing), socket.io-client integration tests, React Testing Library, Playwright E2E incl. iPhone/Pixel device profiles
- Deploy (decided Oct 4, 2026): a private site on one Fly.io machine with auto stop/start (at most one machine), SQLite on a Fly volume via Drizzle with Litestream backups, a shared site password in front (`SITE_PASSWORD`, decided Oct 6, 2026; Cloudflare Access with an own domain stays possible later). One Docker image, one Node process serving the built client + Socket.IO on the same port. The machine stops when nobody is connected: never rely on a timer firing while players are away (store deadlines, check them on load). Postgres and several machines only if Platform 07 happens. Deploy files: `Dockerfile`, `fly.toml`, `deploy/start.sh` (Litestream restore + replicate), `deploy/litestream.yml`; the step-by-step is in `docs/reference/sharing-and-deployment.md` ("Going live"). The server checks the Cloudflare Access token (`access.ts`; on when `CF_ACCESS_TEAM_DOMAIN` and `CF_ACCESS_AUD` are set) on pages and socket handshakes, so `<app>.fly.dev` cannot skip the login; `/health` and `/robots.txt` stay open; every response says `noindex`. The site password gate (`siteGate.ts`, on when `SITE_PASSWORD` is set): `GET /auth/status`, `POST /auth/login` (5 wrong tries lock an address for 5 minutes) give a signed httpOnly cookie for 30 days, renewed on each visit, keyed on the password so a new password signs everyone out; the socket handshake needs it; the client shows `SitePassword` before anything else (`siteAccess` in the store) and connects only once open. Server logs go through pino (`log.ts`, JSON lines, `LOG_LEVEL`; silent in unit tests, warnings only in Playwright because writing to a piped stdout blocks on Windows and slowed the iPhone tests; never log tokens); Sentry only when `SENTRY_DSN` / build argument `VITE_SENTRY_DSN` are set.

## Architecture rules (do not break)

- The server is the referee. Clients send intents only (`match:move { matchId, seq, move: { type: 'place', dieId, slot, coffeeDelta } }`); the server validates with the shared rules and broadcasts.
- All game rules live as pure functions in the game's rules package, Sky Team's in `games/sky-team/rules` (`createGame`, `rollDice`, `canPlaceDie`, `placeDie`, `resolveRound`, `checkLanding`). No rules in React components or socket handlers. The client highlights moves with `canPlaceInView`, which runs the same `checkPlacement` on the player's view.
- `viewFor(state, seat)` is the ONLY way state leaves the server. A player never receives the partner's unplaced dice values, the RNG seed, or future rolls.
- Seedable RNG (`nextRandom` in `@platform/engine`; Sky Team's `rollDie` in shared); tests use fixed seeds. Log every accepted move for replay.
- Engine contract (Platform 01–02): `packages/engine` holds `GameDefinition` (`setup({ config, seats, host, seed, previous })`, `actors`, `validate` / `apply` with a context `{ by, at }`, `view(state, viewer, now)`, `schedule`, `outcome`, Zod `configSchema` / `moveSchema` for client moves only), the table moves (`table:join`, `table:choose-seat`, sent by the platform as `'system'`), `runDue` / `nextDue`, and the test kit (`@platform/engine/testing`). It never imports a game. Sky Team's adapter is `skyTeam` in `games/sky-team/rules/src/definition.ts`, imported only as `@sky/rules/definition` (never from the shared index, so the client bundle stays without it); seat moves `pick-ability`, `confirm`, `ready`, `place`, `spend-reroll`, `reroll`, `ability`, `cancel-swap`; system moves `roll` (Total Trust) and `time-up`, both from `schedule`. A rule change must keep `definition.test.ts` (the kit on every scenario) passing.
- Everything is a move (Platform 02): every change to a game goes through `rooms.move` (a player) or the scheduler (`RoomManager.arm` → `runDue` → `onScheduled`); the handlers never change `room.game` themselves. `rooms.ts` imports only the engine and the registry `games.ts`; Generic protocol (Platform 03): `packages/protocol` holds the events (`room:create { name, game, config }`, `room:join`, `room:rejoin`, `room:leave`, `room:choose-seat`, `room:rematch { matchId, config }`, `match:move { matchId, seq, move }`; server → client `room:presence`, `match:view { matchId, version, view }`), their Zod schemas and the error codes; `handlers.ts` imports no game code. The registry (`games.ts`) maps a game id to its definition, its lobby schema (what a client may choose) and the server's settings for it (`RoomOptions.settings`, e.g. `roundTimerMs`), merged into the config by `configFor`. Sky Team's protocol types are aliases in `games/sky-team/rules/src/events.ts`. The crew's choices live in `GameState.crew` (`crew.ts`: host, seated, `rolesChosen`, picks, confirmed, ready) and reach clients in the view; presence carries only `name`, `online`, `creator`.
- Client shell (Platform 05): routes (TanStack Router, file-based since Platform 06: one file per page in `packages/web/src/routes/`, compiled by `@tanstack/router-plugin` into `src/routeTree.gen.ts`, which is committed and left out of Prettier and ESLint; `router.tsx` builds the router from it; the seated-player redirect is `toOwnRoom` in `ownRoom.ts`): `/` game picker, `/play/:gameId` that game's lobby (name, the game's `SetupForm`, create), `/history` the signed-in account's Flight Log (one section per game, drawn by the game module's optional `History`; signed out it asks to sign in; linked from the account menu), `/r/:code` a room (join form for an invite link, the waiting room while a seat is empty, then the game's `Board`); a seated player is redirected to their room; leaving goes back to `/play/<game>`. A game's client module (`GameClientModule` in `@platform/ui/game`: `Board`, `SetupForm`, `WaitingInfo`, `locales`, `connect`, `onView`, `History`, `reset`, `errorText`) is a lazy chunk named after the game (`assets/sky-team-*.js`), listed in `packages/web/src/games.ts`; the first page load never contains a game's code. The shell's store (`usePlatform`: connection, session with the game id, the latest match view, presence) is separate from each game's (`useSkyTeam`: selection, coffee, intern, reroll picks, timers, the Flight Log), which follows views through `onView`. Games reach the server only through the injected `PlatformApi` (`send`, `chooseSeat`, `rematch`, `leave`, `signedIn`, `flightLog(game)`, `importFlightLog(game, records)`). The shell's `index.css` is the one Tailwind entry: it imports each installed game's `styles.css` and `@source`s its folder.
- Modules only through hooks: a module's rules live in its `RuleModule` (`games/sky-team/rules/src/modules`), its slots declare `module` (or `coveredBy`) in `slots.ts`, and its state is a public `GameState` field. `rules.ts` calls hooks; it never tests for a module by name.
- No in-game chat (removed at the user's request): players talk outside the app in the strategy phase and press "Roll dice"; do not add chat back unless asked.
- Rooms and matches are saved between restarts (Sky Team 12, then the match log of Platform 04): `MatchStore` in `packages/server/src/store.ts` (`SqliteMatchStore` through Drizzle when `DATA_DIR` is set, `MemoryMatchStore` in tests, nothing saved otherwise). A room is one JSON row in `rooms` (format `ROOM_FORMAT` 4: game id, players with a hash of their rejoin token, never the token, their last `seq` and, signed in, their `userId`, the `config`, the current `match`); its game is a log: `matches` (game, `rules_version`, config, seed, status open/over/abandoned, outcome), `match_seats`, `match_moves` (every accepted change, numbered by the match's version) and `match_snapshots` (the state after setup, every `SNAPSHOT_EVERY` = 50 changes, at the end, and for every open match on shutdown). `RoomManager.accept` writes each move synchronously before the broadcast; the room row is saved on the next tick (`rooms.save`, from `broadcastRoom`); closing or sweeping a room deletes its row and abandons its open match; finished matches stay, ended matches are deleted with their log after the game's own `keepEnded` times (registry, `games.ts`; Sky Team: abandoned after 1 day, finished after 30 days, since each player's Flight Log is the lasting record; a game without one keeps them), run by the room sweep. On start, each room loads with everyone offline, its game rebuilt by `restoreMatch` (latest snapshot + later moves; an older `rules_version` goes through `migrate`, or the room is dropped), idle ones are swept, and `rooms.arm` re-arms timers (a passed deadline expires at once). Format-3 room rows (whole game inside) are converted into a room plus a match on first start. The schema is the `MIGRATIONS` list (SQLite `user_version`): only add steps at the end. Never change the meaning of a stored move; a rules change that does bumps the game's `version` and adds `migrate`. Run a single server instance.
- `GAME_SEED` (fixed dice), `E2E_HOOKS` (test-only `POST /__e2e/rooms/:code/game`) and `ROUND_TIMER_SECONDS` (short timed rounds) exist for tests and dev and are ignored when `NODE_ENV=production`; never enable them on a public server.
- Optional round timer (creator's choice in the lobby, off by default, 3 min): the rules own it (`startRoundTimer`, `expireRoundTimer`, `roundTimeLeft`; the deadline clears when a round or the game ends) and the server enforces it (`schedule` returns `time-up` at the deadline; one timer per room via `rooms.arm`, plus `runDue` before every player move). Views send the time left, never the absolute deadline; the client countdown is display only.
- Accounts (Platform 06, optional; guests play as before): Better Auth in `packages/server/src/accounts.ts` on the platform's SQLite connection (`openDatabase` in `store.ts`, shared with the match store; in memory without `DATA_DIR`), tables `users`, `auth_sessions`, `auth_accounts`, `auth_verifications` (`MIGRATIONS` step 3, snake_case columns mapped in `accounts.ts`). Sign in with Google. Better Auth answers under `/api/auth/*`, `GET /auth/me` returns the user or `null`; both sit behind the site password. Session cookie `platform.session_token` (httpOnly, Lax, Secure in production), apart from `site_auth`. Sign-in rate limit per address from the server's own reading of the address (`requestIp`); Better Auth's log messages only (never its arguments). `GET /auth/methods` says which sign-ins are on; the display name starts as Google's (cut to 20 characters) or is asked once if Google provides none, and can be changed from the account menu with `POST /auth/name` (Better Auth's `/update-user` is off); rooms already seated keep the old name until the next game. Seats follow the account (Platform 06 D): the socket's account is read at the handshake (`io.use` in `app.ts`, `socket.data.userId`; the client reconnects after signing in or out, `accountChanged` in `api.ts`); `Player.userId` and `match_seats.user_id` (`MIGRATIONS` step 4) name it; `room:resume` gives a signed-in device the account's seat (most recently active room, new token), joining your own room's code gives your seat back (never both seats), and a guest seat is linked on the first rejoin after signing in. Guests keep tokens only. The Flight Log per account (Platform 06 E): when a match ends, `RoomManager.endInLog` writes one `flight_log` row per signed-in player (`MIGRATIONS` step 5, key user + match, `INSERT … DO NOTHING` so a restart never writes twice) from the game's registry entry `flightRecord(view, others, at)` (Sky Team: `recordOf` in `@sky/rules`, the same record a guest keeps on the device); the table outlives the pruned match log. `GET /api/flight-log?game=<id>` returns the caller's own rows, newest first (site password, `401 signed-out`). `POST /api/flight-log/import` takes a device's games from before sign-in (each game's `importRecord` checks them; the key is game + scenario + seat + end time, so a second device adds nothing twice); Sky Team's store sends them on the first sync when signed in and clears the device copy only when the server accepted them. Sky Team's store reads it through `PlatformApi.flightLog()` when signed in (`syncHistory`: on opening the Flight Log, the scenario picker and at game over) and `localStorage` otherwise; signed in, a finished game is not also saved on the device. `DELETE /api/account` (menu "Delete account", after a confirmation) removes the user, its sessions and provider links, its `flight_log` rows and its `user_id` on `match_seats` and in live rooms (`RoomManager.forgetAccount`); the games themselves stay. In the shell: `account` in `usePlatform` (`'loading'`, `'off'`, or methods + user; `src/account.ts`, loaded after the site password), "Sign in" / the name and its menu on the picker and game pages (`screens/Account.tsx`, `CardTop account`), the name asked once in a dialog, and signed-in name fields read-only. Settings: `AUTH_SECRET`, `AUTH_URL`, `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`.
- Closing a tab only marks a player offline (seat kept); `room:leave` gives the seat up. Rooms nobody is connected to are swept after `ROOM_TTL_MINUTES` (30) idle; `ROOMS_PER_IP` (5) caps live rooms per creator IP (`TRUST_PROXY=1` behind a proxy).
- Repeated requests must be harmless: a `match:move` whose `seq` the server already accepted from that seat is a no-op (`{ ok: true }`), a second "Fly again" for a match already replaced is OK, and the client never sends the same request twice while one is pending.

## UI rules

- Mobile-first. Custom Tailwind breakpoints in `@theme`: `tablet` = 600px, `desktop` = 1024px.
- Phone portrait: status bar, tracks strip, scrolling cockpit, dice tray fixed at bottom. Tablet: two columns (tracks + cockpit / dice tray). Desktop: one centred container (max 72rem): tracks side by side above the cockpit, dice tray below; not full width. Axis and Engines are one panel, "Axis & Engines" (`FlightInstrument`): the axis dial on the upper half, the speed 2–12 on the lower half (one segment per value, grey / blue / orange by how far the plane flies; the gaps after the blue and orange aerodynamics markers take their colour; the speed is a black dot with its number in white), and red brake sections outside the lower half (normal brakes up to 2, 4, 6; Ice brakes up to 2, 3, 4, 5); Axis spaces at the top corners, Engine spaces at the bottom ones, "+N wind" in the middle. Desktop cockpit (`desktopGrid` in `components/cockpit/layout.ts`, CSS variables on `.cockpit-grid`): Landing gear left and Flaps right share the top row (same height, set by their content); Axis & Engines spans two rows with Wind and one Radio panel (co-pilot spaces above the pilot's) beside it; Brakes (or Ice brakes) and Concentration split the centre below; Kerosene and Intern each get a full-height column left of Flaps; Alarms a row under the centre. Below desktop the cockpit order depends on the seat (`sectionOrder` in `components/cockpit/layout.ts`), every panel full width: pilot = Wind, Axis & Engines, Alarms, Landing gear, Brakes (or Ice brakes), Kerosene (or leak), Intern, Radio, Concentration, Flaps; co-pilot = Wind, Axis & Engines, Alarms, Radio, Concentration, Flaps, Ice brakes, Kerosene (or leak), Intern, Landing gear, Brakes (plain brakes go last); Radio and Concentration share a row below desktop. Column spans use `max-desktop:` so they never fight the desktop grid areas. Ordered switches (flaps, brakes) show arrows between slots. Kerosene: its space above the gauge (vertical in the desktop column). Ice brakes: between the rows, a bar per brake that fills green (sliding open) once deployed, with arrows between the bars (progress also shows on the brakes arc). Concentration slots (either player) are half blue, half orange (`.slot-shared`). Gear, flaps and brakes show a toggle `Switch` (svgs/Switch.tsx), not a light. A panel hint sits behind an info icon next to the title (popover; gray, red on the mandatory Axis and Engines, whose popover also explains "Mandatory"); panels without a hint have no icon. On the approach track, a space with both a traffic die and a turn stacks them (die above, turn dots below).
- After each round's last die (game not over), a green "Next turn in 5s" countdown is the only status pill for 5 s, in every game (`nextTurnAt` in the store, `NextTurnCountdown`): the board keeps showing the finished round (`lastRound`) and "Roll dice" (in the dice tray) is disabled until it ends. While dice are placed, a red "No talking" pill sits next to the turn label. Countdowns share `useNow`.
- Modules: Kerosene and Intern panels are cockpit sections (ordered per seat below desktop; one row, half each, under the control panel on desktop); Wind is its own panel (first on phones, beside Axis & Engines on desktop); Ice brakes replace the Brakes panel (radio and brakes then take a full row each below desktop). Training the intern takes two taps: the Intern space, then where its token goes (`internSlot` in the store). The co-pilot's tray shows the black traffic die for Synchronization; Adaptation, Anticipation and Working Together buttons appear under the selected die when `canUseAbilityInView` allows. The lobby and the game-over dialog share `ScenarioPicker` (scenario only). Games start in the `setup` phase: a "Before take-off" panel above the tracks (`Preflight`) where the creator chooses the seats (`room:choose-seat`; Pilot / Co-pilot outline buttons, each player's own seat solid once chosen), the Special Ability cards are picked (two cards: one each; one card: the creator's; the `pick-ability` move), and both press Confirm (the `confirm` move); round 1, traffic die included, starts when both have confirmed (`beginGame`). The picks live in `game.crew.picks` and are copied into `game.abilities`; a rematch keeps the picks of those still seated. From the round before the final one, the dice tray shows a "Win conditions" popover listing `landingConditions(scenario)` (shared rules: the base five plus each module's `landingConditions`).
- Turbulence: Alarm board panel after Engines (both seats; full row on desktop); a blocked space shows a red bell; weather icons on altitude cards and a weather note plus face-down set-aside dice in the tray; Alarm (bell) and Total Trust (muted speaker) symbols at the top corners of approach cards; Total Trust hides "Roll dice"; covered spaces (stuck gear) show a grey X.
- Text: every client string goes in `en.json`, `vi.json` and `fr.json` (same keys) of its namespace: the shell's in `packages/ui/src/locales` (namespace `platform`, the default: `useTranslation()`), each game's in `games/<id>/client/src/locales` (namespace = the game id: `useTranslation('sky-team')` in components, `t` from the game's `i18n.ts` in helpers); plurals `_one`/`_other`. The game picker names a game from the platform's `games.<id>` keys (before its module loads). The server sends codes, never sentences. English is the default; `LanguageSwitch` saves each player's choice in `localStorage`. Tests run in English.
- On `visibilitychange` to visible: reconnect and `room:rejoin` with the saved token.

## Workflow

How much to test: the full run (`pnpm test` + `pnpm e2e`) only at the end of a phase (below). Small UI tweaks (labels, styling, animations): typecheck, format and lint only; tests when the user asks. Other changes outside a phase: only the affected package's tests (`npx vitest run --project @sky/client`, `@sky/rules`, `@platform/web`, `@sky/server`, `@platform/engine` or `@platform/protocol`; one file or `-t "<name>"` for a single test), and one Playwright test (`-g "<name>"`) only if the change is visible in a full game. CI still runs everything on every push to `main`.

When a phase is done (its "Done when" check verified, plus `pnpm test`, `pnpm typecheck`, `pnpm lint`, `pnpm format:check` and `pnpm build` passing):

- Tick that phase's checklist in its `docs/epics/<epic>/phase-NN-*.md` file. Leave unfinished items unticked and say why. Add a "✅ Verified <date>" note to its "Done when" line, and update the phase's status in the epic's `EPIC.md` table (and the epic's row in `docs/PLAN.md` when the epic's status changes). `docs/PLAN.md` "Order" has two Mermaid diagrams: the epics, and the current epic's phases; update their status marks too, and switch the second one to the next epic when an epic is done.
- Update the docs so they match the code: the relevant `docs/reference/` files (protocol, game rules and assumptions, UI, testing, deployment), later phase files affected by work pulled forward, and this file (stack, commands, rules) when they changed.

## Commands

- `pnpm dev` — server (port 3000, `tsx watch`) + Vite together; Vite proxies `/socket.io`, `/health`, `/auth` and `/api` to the server
- `pnpm dev:lan` — like `pnpm dev`, but Vite listens on the LAN (`--host`) so a phone can open the Network URL it prints
- `pnpm build` — production build of every package (`pnpm -r build`: shared `tsc`, server `tsup`, client `tsc -b && vite build`)
- `pnpm start` — run the built server (`packages/server/dist/index.js`), which also serves the built client; set `NODE_ENV=production` for anything shared, and `DATA_DIR=<folder>` to save games in `<folder>/boardgames.sqlite`
- `pnpm test` — Vitest, all packages; `pnpm test:watch` to re-run on change
- `pnpm e2e` — Playwright: builds, starts the production server on port 3100 (`GAME_SEED=1`, `E2E_HOOKS=1`) and runs `e2e/` on Desktop Chrome, iPhone 13 (WebKit; its checks wait up to 15 s, the others 5 s, because WebKit is slow to draw the board under a full parallel run), Pixel 7; `pnpm exec playwright test -g "<name>" --project "Desktop Chrome"` for one test
- `pnpm typecheck`, `pnpm lint`, `pnpm format:check` — same checks as CI; `pnpm format` fixes formatting
- `pnpm lighthouse` — mobile Lighthouse audit of the build (Lighthouse CI; runs in CI on Linux, fails on Windows cleanup)
- `pnpm --filter @sky/rules random-play [games] [firstSeed] [scenario id | all]` — play random games (YUL by default) and print how they ended
- `pnpm --filter @platform/web preview` — serve the built client alone with Vite (no game server)
- `pnpm exec playwright install chromium` — one-time browser download for Playwright
- Cloudflare tunnel by hand (two PowerShell terminals; details in `docs/reference/sharing-and-deployment.md`):
  - Terminal 1: `pnpm build; $env:NODE_ENV = 'production'; $env:TRUST_PROXY = '1'; pnpm start` — wait for `server listening on http://localhost:3000`
  - Terminal 2: `cloudflared tunnel --url http://localhost:3000` (or `& "C:\Program Files (x86)\cloudflared\cloudflared.exe" tunnel --url http://localhost:3000`) — the `https://*.trycloudflare.com` line is the link; Ctrl+C in both to stop

## Shortcuts

- **"run tunnel"**: share the current build on a public link (manual steps for the user: `docs/reference/sharing-and-deployment.md`).
  1. Check port 3000 is free; if something is listening there, say what and ask before touching it.
  2. `pnpm build`.
  3. In the background: `NODE_ENV=production TRUST_PROXY=1 PORT=3000 node packages/server/dist/index.js`; wait until `http://localhost:3000/health` answers.
